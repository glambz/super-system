## Task S: scripts

Files allowed: `skills/super-system/scripts/run-codex.sh`, `skills/super-system/scripts/removed-checks.py`, `tests/check_scripts.py`.

### Item 1: `run-codex.sh` retries only on real rate limits

Evidence: the rate-limit check greps the whole event stream. The stream holds the agent's own output (file contents, command output), which often mentions "429" or "rate limit". Three finished scouts were re-run four times each and emptied the provider's quota window. The script also stopped before writing its meta file when the answer was not JSON, which looked like a stall.

Required behaviour:

1. **Where to look.** The rate-limit check reads only (a) the stderr log and (b) lines of the event stream that are top-level events of type `error` or `turn.failed`. It never reads agent output (`item.*` events or any other line).
2. **What counts.** Case-insensitive: `429` not inside a longer number, `rate limit` (joined by a space, `_`, `-` or nothing), `usage limit`, `quota`, `high demand`, `temporary errors`. The retry policy stays: sleep `RETRY_SLEEP` seconds (default 300), at most 3 retries.
3. **Meta file first.** When the answer file is missing, is not JSON, or is not a JSON object, the script still writes `<name>.meta` (exit code and thread id), prints an error to stderr and exits non-zero. The answer is judged only after the meta file is written.

A copy with exactly these three changes ran 20 reviews without a false retry: `~/.super-system/runs/todo-list-app-20261113-134602/scripts/run-codex-v3.sh`. Port its changes. Drop its `v2:` / `v3:` comment markers (they name run-local versions) and keep the usage line naming `run-codex.sh`.

Tests (`tests/check_scripts.py`, stub `codex`, `RETRY_SLEEP=0`); each must fail on the base script:

- **No false retry:** the stub prints an `item.completed` event whose text contains `HTTP 429 rate limit exceeded, quota`, writes a valid answer and prints `turn.completed`. Expect exit 0 and exactly one `codex` call.
- **Real limit in the event stream:** the first call prints a top-level `error` event whose message contains `high demand` and writes no answer; the second call succeeds. Expect exit 0 and exactly two calls.
- **Real limit in stderr:** the same, with `usage limit` written to stderr on the first call and no error event.
- **Unparsable answer:** the stub writes `not json` as the answer and completes the turn. Expect a non-zero exit and a meta file that holds the thread id.

### Item 4: `removed-checks.py` lists removed deny branches

Evidence: a task removed an organisation gate (`if task.organization_id not in org_ids:` / `return False`) and the guard listed nothing. The orchestrator also once passed `--` before the files and got an empty list (git saw a second `--` as a path).

Required behaviour, added to today's patterns (which stay):

1. A removed line is listed when it contains `not in` (as words), `return False`, or a returned error object (`return {"error"` or `return {'error'`, any spacing).
2. A removed `return None` or bare `return` is listed only when it sits on an `if` / `elif` line, or when the removed line directly before it in the same hunk is an `if` / `elif` line. A `return None` elsewhere is not listed (too noisy).
3. A `--` among the arguments after `<base>` is ignored; the script adds its own.
4. The output format (`file:line: content`), the exit codes and the handling of quoted and spaced paths stay. The usage text names what is matched.

Tests (`tests/check_scripts.py`, extend the existing functional test); each new assertion must fail on the base script:

- every line of rules 1 and 2 is listed with its file and line;
- a removed `return None` that follows a plain assignment, and the existing unrelated line, are not listed;
- a call with `--` before the file prints the same list as the call without it.

### Item 2: full suite before each review (`references/runners.md`, "Is it done?", item 5)

Evidence: 3 of 7 failed reviews were existing tests elsewhere that a new rule broke; implementers had run only focused tests.

Add one bullet after "Base-diff guard":

> **Full-suite check:** before dispatching the reviewer, run the project's full test suite in the task's worktree (in the background) and compare its failures with the known-failing list in the brief's hard constraints. Put every new failure into the reviewer's brief; the reviewer confirms each one and reports it as a finding. In `economy` workflow mode skip this: the full suite runs once at the end (`references/modes.md`).

### Item 3: shared-helper check in the fix plan (`references/flows/fix.md`, step 3)

Evidence: two findings changed a shared helper whose other callers sat in files outside every task; both needed a scope decision in the middle of the run.

Add to step 3 ("Fix plan"):

> When the fix changes a shared helper (a function, component or module that other code calls), list every file that calls it: each is in some task's files allowed, or the plan says why it needs no change.

### Item 5: reviewer answer fields (`references/schemas/reviewer.json`, `references/roles/reviewer.md`, `references/runners.md`)

Evidence: reviewers were told to confirm each removed check, but the schema had no field for it; five reviewers put it in `not_checked`. One `fix` reviewer returned `regression_checks: null` and still passed.

1. **Schema.** Add a required property `removed_checks`: an array of objects, each with `line` (string: the removed line as listed in the brief), `safe` (boolean) and `reason` (string). Description: one entry per line of the brief's removed-checks list; an empty array when the brief has none. `regression_checks` becomes a plain array (no `null`): one entry per regression test in the `fix` flow, an empty array in other flows. Every object stays strict (`additionalProperties: false`, all properties required).
2. **Reviewer role.** Add one "How you work" bullet: for each line in the brief's removed-checks list, record in `removed_checks` whether the removal is safe and why (replaced by an equal or stricter check, moved, or dead code); an unsafe removal is also a finding. In the "Your answer" sentence, name `removed_checks`, and change "`regression_checks` (populated in `fix`, `null` otherwise)" to say: one entry per regression test in `fix`, an empty array otherwise.
3. **Done check** (`references/runners.md`, "Is it done?", item 4, reviewer). Replace "`regression_checks` is populated in `fix`" with: in `fix`, `regression_checks` has an entry for every test in the implementer's `red_evidence`; `removed_checks` has an entry for every line passed from the base-diff guard. A missing entry is handled like a missing `verdict` (rerun fresh once, then a blocker).
4. **Base-diff guard** (`references/runners.md`, item 5). Change the end of its sentence from "who must confirm each is safe or reject" to: who records each in `removed_checks` as safe, or reports it as a finding.

### Item 6: no secrets in scratch copies (`references/roles/reviewer.md`, `references/runners.md`)

Evidence: two reviewers copied the project's `.env` into their scratch folders to run tests on a base copy, and left it there.

1. **Reviewer role**, under "You must not": never copy env or credential files (`.env`, key files, service-account files) into your scratch folder; when a test on the base copy needs a setting, give it a stub value.
2. **Orchestrator** (`references/runners.md`, "Is it done?", item 5, the reviewer bullet): when a review ends, delete any env or credential file left under its scratch folder (for example `scratch/**/.env`).

### Item 7: fix briefs state the invariant (`references/runners.md`, "Briefs", the "Fix rounds" bullet)

Evidence: a fix brief told the implementer which mechanism to use; the mechanism was controlled by the caller and the fix created a critical bypass.

Append to the bullet:

> For each finding, the brief states what must hold after the fix (the invariant, for example "no input the caller controls can trigger the exemption"). It never prescribes a mechanism the orchestrator has not verified in the code.

### Item 9: polish groups may start early (`references/modes.md`, "Minor triage")

Evidence: all polish work waited for the last task although most polish files were free hours earlier.

Add after the sentence that defines the polish round (which stays, as the default):

> A polish group may start early when its files don't overlap the files allowed of any task that is still running or waiting to run; minors decided later go into one last group.
