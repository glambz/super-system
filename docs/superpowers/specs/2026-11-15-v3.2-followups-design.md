- `skills/super-system/SKILL.md` is not changed (8179 bytes; `tests/check_skill.py` caps it at 8192).

## Task S: scripts

Files allowed: every file in `skills/super-system/scripts/`, and `tests/check_scripts.py`.

### Item 3: shipped helpers do not depend on the console code page

Evidence: on Windows, Python that writes to a pipe uses the console code page (cp1252). In the v3.2 run this crashed a new filter in `run-codex.sh` and made `removed-checks.py` output unreadable as UTF-8; both were fixed there. The other helpers were not checked.

What must hold, for every Python file in `skills/super-system/scripts/` and every inline Python block in its shell scripts:

1. Text it prints is UTF-8 or ASCII-only, whatever the console code page or locale.
2. Text it reads from a file or from another program is decoded explicitly, never with the locale's default.
3. No input makes it crash with an encoding error: file names or content with characters outside the code page (an emoji, CJK text), or invalid UTF-8 bytes.
4. Its behaviour, output format and exit codes are otherwise unchanged.

How to work:

- Audit every script and list each Python block in your `summary`: what it prints, what it reads, and whether it needed a change.
- Change only where you can show a defect with a failing test. A block that already meets the four points stays untouched (for example one that prints only `json.dumps` output with its default ASCII escaping).
- Known candidate: `review-wrap.sh` reads `git` output with the locale's default encoding and prints file names.

Tests (`tests/check_scripts.py`): for each change, a test that fails before it. Use a forced non-UTF-8 output encoding (for example `PYTHONIOENCODING=ascii` in the test's environment) and a file whose name or content holds an emoji and CJK text, so the test fails on every platform and not only on Windows. Read the scripts' output as UTF-8.
